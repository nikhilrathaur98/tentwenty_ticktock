# ticktock – Timesheet Management App

A small SaaS-style timesheet app built for the TenTwenty Frontend Technical Assessment.

**Live demo:** https://tentwenty-ticktock-amber.vercel.app/
**Demo login:** `john@example.com` / `password123`

## Features

- Login with email and password (NextAuth credentials provider, JWT session stored in an HTTP-only cookie)
- Protected dashboard: signed-out users are redirected to `/login`
- **Timesheets table**: Week #, Date, Status, Actions
  - Filter by date range (a range covering several weeks returns all of those weeks)
  - Filter by status
  - Sort by week/date or status
  - Pagination with 5 / 10 / 20 rows per page
- **Week view**: the tasks for each working day, with a progress bar for hours logged
- **Add / Edit modal** with form validation (client and server), plus Delete with confirmation
- Loading, empty and error states with retry
- Responsive layout (mobile, tablet, desktop)
- Unit and component tests

## Getting started

Requirements: Node.js 20.9 or newer, npm.

```bash
git clone https://github.com/nikhilrathaur98/tentwenty_ticktock.git
cd tentwenty_ticktock
npm install
```

Create a `.env.local` file in the project root:

```
NEXTAUTH_URL=http://localhost:3000
NEXTAUTH_SECRET=any-long-random-string
```

Then run:

```bash
npm run dev
```

Open http://localhost:3000 and sign in with `john@example.com` / `password123`.

## Project structure

```
data/
  seed.json                 Demo users, projects and entries (generated by scripts/seed.mjs)
scripts/
  seed.mjs                  Generates the seed data
src/
  app/
    login/                  Login screen
    (dashboard)/            Pages that need a signed-in user (shared header + footer)
      timesheets/           Timesheets table
      timesheets/[week]/    Week view
    api/
      auth/[...nextauth]/   NextAuth endpoints
      timesheets/           GET list (filters, sort, pagination)
      timesheets/[week]/    GET one week with its entries
      entries/              POST create entry
      entries/[id]/         PUT update / DELETE entry
      projects/             GET projects and types of work
  components/
    ui/                     Reusable building blocks (Button, Modal, Select, Pagination...)
    layout/                 Header, user menu, footer
    auth/                   Login form
    timesheets/             Table screen components
    week/                   Week view and entry modal components
  hooks/                    Data fetching hooks (useApi, useTimesheets, useWeekTimesheet)
  lib/                      Business logic, database access, auth config, validation
  types/                    Shared TypeScript types
```

### How data flows

```
Component -> hook (useApi) -> fetch("/api/...") -> Route Handler -> lib/db.ts -> JSON file
```

- The browser never reads the JSON file directly. Every request goes through an internal API route.
- Each API route checks the NextAuth session and only returns the signed-in user's data.
- `lib/validation.ts` is used by both the form and the API, so the rules are always the same.
- Timesheet statuses are calculated from entries, not stored.

## Assumptions and notes

- **Weeks**: a timesheet week is Monday to Friday. Week 1 starts on Monday 29 December 2025 (the Monday of the week containing 1 January 2026), and there are 52 weeks. Some dates in the design (for example "28 January - 1 February") look like placeholders, so real calendar weeks are used instead.
- **Statuses**: `completed` = 40 or more hours, `incomplete` = between 1 and 39 hours, `missing` = 0 hours.
- **Actions**: View, Update and Create all open the week view. Entries can be added, edited and deleted in every week.
- **Hours**: each entry is a whole number from 1 to 24.
- **Authentication** is dummy auth, as the brief allows. Users and plain-text passwords live in `data/seed.json`. A real app would hash passwords and use a real database.
- **Remember me** is shown to match the design. NextAuth's default 30-day session is used either way.
- **Data storage**: locally, changes are saved to `data/db.json`, which is git-ignored and created from `seed.json`. Vercel's file system is read-only, so in production the database is copied to the server's temporary folder. Changes work during a session, but they can reset when Vercel starts a new server instance. A real database (for example Postgres or Redis) would fix this.
- The progress bar percentage is `hours logged / 40`.
